# 三位一体规则链状态标签 UX 设计

## 0. 目标

本设计用于优化分析页中“`三位一体规则链`”的状态表达方式。

当前规则链已经能展示六段规则，但右上角状态标签使用的是：

- `通过`
- `警示`
- `提示`
- `失败`

这些词更像系统内部判定语言，而不是交易用户语言。用户虽然能看到颜色和标签，但很难第一眼回答以下问题：

1. 这张规则卡现在是偏多、偏空，还是中性？
2. 这条规则现在到底是能做、先看、谨慎，还是不要做？
3. 这个状态为什么会是这样？

本次改造的目标是把规则链状态改成 **交易语言主导、规则语言辅助、颜色表达方向** 的用户表达方式。

## 1. 问题定义

当前规则链存在三个体验问题：

### 1.1 状态词是系统语言，不是交易语言

`通过 / 警示 / 提示 / 失败` 更适合给开发者或策略调试者看，不适合给交易用户看。

用户看到这些词后，仍然需要自己翻译成：

- 是不是可以动手？
- 是继续等？
- 是有风险但还能看，还是已经不能做？

### 1.2 颜色同时承担了“状态”和“方向”两种语义

当前颜色主要跟状态走，例如：

- 绿色表示 `通过`
- 黄色表示 `警示`
- 蓝色表示 `提示`
- 红色表示 `失败`

但在交易语境中，用户天然会把颜色理解成方向：

- 红色 = 偏多 / 看多
- 绿色 = 偏空 / 看空

这会导致颜色语义和状态语义冲突。

### 1.3 当前已有规则释义，但没有“状态释义”

标题右侧的 `i` 图标已经能解释“这条规则是什么”，例如结构资格、量能确认、执行计划的含义。

但用户仍然不知道：

- `观察中` 到底是什么意思？
- `谨慎看` 和 `暂不做` 有什么区别？
- 这张卡当前为什么显示成这个状态？

因此，规则链还需要一层专门解释“当前状态”的 hover。

## 2. 本次设计结论

本次采用 **三层表达**，但不使用三枚并列标签，避免页面拥挤：

1. **颜色层**：表达方向
   - 红色 = 偏多 / 看多
   - 绿色 = 偏空 / 看空
   - 灰色 = 中性 / 等待 / 无明确方向

2. **主标签层**：表达交易可执行度
   - `可执行`
   - `观察中`
   - `谨慎看`
   - `暂不做`

3. **Hover 解释层**：表达规则满足度和当前原因
   - 规则状态：`已满足 / 待确认 / 有约束 / 不成立`
   - 交易含义：用户下一步该怎么理解
   - 当前方向：偏多 / 偏空 / 中性
   - 当前原因：引用该卡当前判定依据

这三层分别回答：

- 颜色：`方向是什么`
- 主标签：`现在能不能做`
- Hover：`为什么是这样`

## 3. 方案比较

### 方案 A：保留旧词，只新增 hover

做法：

- 保留 `通过 / 警示 / 提示 / 失败`
- 给状态词增加 hover 解释

优点：

- 改动最小
- 测试和数据契约改动少

缺点：

- 核心词本身仍然难懂
- 用户第一眼问题仍未解决
- 只是补救，不是根本优化

### 方案 B：同时展示三枚标签

做法：

- 一枚标签表达方向，如 `偏多`
- 一枚标签表达交易动作，如 `观察中`
- 一枚标签表达规则状态，如 `待确认`

优点：

- 信息完整
- 一眼能看到三层语义

缺点：

- 卡片头部过于拥挤
- 六张卡并排时视觉噪音太大
- 信息虽然全，但扫描效率反而下降

### 方案 C：颜色表达方向，主标签表达交易动作，hover 解释规则状态（推荐）

做法：

- 卡片颜色只负责表达方向
- 右上角主标签只保留交易语言
- 标题 `i` 继续解释“这条规则是什么”
- 主标签 hover 解释“这个状态是什么意思”

优点：

- 第一眼能快速回答“偏多还是偏空”“现在能不能做”
- 不需要堆 2~3 枚 badge
- 与当前页面结构兼容最好

缺点：

- 用户需要 hover 才能看到“规则状态”全文
- 需要把方向语义从状态语义中拆开

本次采用 **方案 C**。

## 4. 状态文案规范

### 4.1 交易语言主标签

规则链中所有用户可见状态标签统一使用以下四个词：

| 内部状态 | 用户主标签 | 用户理解 |
| --- | --- | --- |
| `passed` | `可执行` | 这条规则已满足，可纳入当前执行判断 |
| `info` | `观察中` | 这条规则尚未完全满足，先继续观察 |
| `warning` | `谨慎看` | 这条规则存在约束或风险，不能直接放大动作 |
| `failed` | `暂不做` | 这条规则当前不支持交易 |

说明：

- 页面主视图不再展示 `通过 / 警示 / 提示 / 失败`。
- 这些词保留在内部状态映射与测试中即可，不直接暴露给用户。

### 4.2 状态含义映射

hover 中统一展示一条“规则状态”辅助语义：

| 用户主标签 | 规则状态 | 含义 |
| --- | --- | --- |
| `可执行` | `已满足` | 当前条件已经达到执行门槛 |
| `观察中` | `待确认` | 当前有方向，但还缺确认 |
| `谨慎看` | `有约束` | 当前并非完全否决，但不能直接执行 |
| `暂不做` | `不成立` | 当前条件不支持按该规则交易 |

### 4.3 可选图标映射

建议给状态标签增加图标，帮助用户更快建立心智：

| 用户主标签 | 图标建议 |
| --- | --- |
| `可执行` | `✓` |
| `观察中` | `○` 或 `眼睛` |
| `谨慎看` | `!` |
| `暂不做` | `×` |

本次实现可先用 lucide 图标或字符方案，重点是图标语义稳定，不强求视觉复杂度。

## 5. 颜色规范

### 5.1 总原则

规则链颜色从本次开始只表达 **方向**，不再表达“通过/提示/警示/失败”。

固定语义如下：

- `红色`：偏多 / 看多 / 多头方向
- `绿色`：偏空 / 看空 / 空头方向
- `灰色`：中性 / 等待 / 无明确方向

### 5.2 不再使用的旧语义

以下旧语义需要废弃：

- 绿色 = 通过
- 黄色 = 警示
- 蓝色 = 提示
- 红色 = 失败

因为这种配色与交易语境冲突，用户天然会把颜色看成多空方向。

### 5.3 组件中的颜色落点

规则链卡片中，以下元素都跟方向走：

- 卡片边框色
- 卡片背景浅色
- 右上角主标签文字/边框色
- 必要时可加标题左侧方向点

颜色不再直接跟 `status` 绑定，而应跟 `direction` 绑定。

### 5.4 状态如何体现

由于颜色不再负责表达状态，所以状态主要通过以下方式表达：

- 主标签文字：`可执行 / 观察中 / 谨慎看 / 暂不做`
- 主标签图标：`✓ / ○ / ! / ×`
- hover 状态说明：`已满足 / 待确认 / 有约束 / 不成立`

这样用户不会再把“黄色 = 警示”误解成某种方向。

## 6. Hover 设计

规则链保留两类 hover，职责分离：

### 6.1 标题旁 `i` 图标 hover：解释“这条规则是什么”

保留当前已有模式。

例如：

- `结构资格释义`
- `MACD 时空释义`
- `执行计划释义`

这类 hover 不解释当前状态，只解释该规则模块本身的定义。

### 6.2 主标签 hover：解释“当前状态是什么意思”

新增一层专门面向用户的状态 hover。

hover 中固定展示四项：

1. `交易含义`
2. `规则状态`
3. `当前方向`
4. `当前原因`

#### 示例：`可执行`

- 交易含义：这条规则已满足，可纳入当前执行判断
- 规则状态：已满足
- 当前方向：偏多 / 偏空 / 中性
- 当前原因：引用该卡片当前判定依据

#### 示例：`观察中`

- 交易含义：已有方向，但还差确认，不急着动作
- 规则状态：待确认
- 当前方向：偏多 / 偏空 / 中性
- 当前原因：引用该卡片当前判定依据

#### 示例：`谨慎看`

- 交易含义：存在约束，不能直接放大动作
- 规则状态：有约束
- 当前方向：偏多 / 偏空 / 中性
- 当前原因：引用该卡片当前判定依据

#### 示例：`暂不做`

- 交易含义：当前不支持按这条规则交易
- 规则状态：不成立
- 当前方向：偏多 / 偏空 / 中性
- 当前原因：引用该卡片当前判定依据

### 6.3 Hover 内容来源

状态 hover 中的“当前原因”优先使用当前卡片的 `reason` 字段。

若 `reason` 为空或不可读，可回退到：

- `detail` 的摘要版
- 或 view-model 显式输出的 `statusExplanation.reason`

## 7. 顶部说明文案优化

当前顶部说明过于偏系统描述，例如：

- `六段规则逐项展示当前状态，失败与警示会被明确保留。`

建议改成更贴近用户的问题表达。

推荐文案：

> `每张卡都会告诉你：当前偏多、偏空还是中性；现在能不能按这条规则动手；若还不能做，还差什么确认。`

若需要保留主判定级别说明，则组合成：

> `本规则链默认按日线主判定展示；若日线缺失，则依次降级为周线、60分钟、30分钟、15分钟。每张卡都会告诉你：当前偏多、偏空还是中性；现在能不能按这条规则动手；若还不能做，还差什么确认。`

## 8. 数据契约调整

### 8.1 现状问题

当前 `AnalysisPageRuleChainItem` 只有：

- `title`
- `status`
- `detail`
- `reason`

这会导致组件层不得不把：

- 状态文案
- 卡片颜色
- hover 含义

都直接从 `status` 推出来。

但本次设计要求“状态”和“方向”拆开，因此需要在 view-model 层显式输出用户展示字段。

### 8.2 推荐契约

建议将规则链展示层数据扩展为：

```ts
interface AnalysisPageRuleChainItem {
  title: string;
  status: 'passed' | 'failed' | 'warning' | 'info';
  direction: 'bullish' | 'bearish' | 'neutral';
  displayStatusLabel: '可执行' | '观察中' | '谨慎看' | '暂不做';
  displayStatusIcon?: 'check' | 'watch' | 'alert' | 'stop';
  detail: string;
  reason: string;
  statusExplanation: {
    tradeMeaning: string;
    ruleState: '已满足' | '待确认' | '有约束' | '不成立';
    directionLabel: '偏多' | '偏空' | '中性';
    reason: string;
  };
}
```

说明：

- `status` 继续保留，便于内部逻辑与测试延续。
- `direction` 专门负责颜色语义。
- `displayStatusLabel` 专门负责用户看到的主标签。
- `statusExplanation` 专门负责 hover 文案，不要在组件里临时拼接。

### 8.3 方向来源原则

方向值 `direction` 不应在组件中通过字符串猜测，而应在 view-model 中明确给出。

优先原则：

1. 若该规则本身有明确方向判断，使用该规则自身方向。
2. 若该规则本身没有明确方向，但受当前主判定方向约束，则回退到 `decision.conclusion.bias`。
3. 若当前规则只表达限制、等待或信息不足，且方向不明确，使用 `neutral`。

这样可避免组件层出现脆弱的关键词推断。

## 9. 页面展示规则

### 9.1 卡片头部

规则卡头部结构调整为：

- 左侧：规则名称 + `i` 图标
- 右侧：主标签（交易语言）

不再并列展示：

- `偏多`
- `已满足`
- `可执行`

三枚标签不同时出现，避免头部拥挤。

### 9.2 卡片正文

正文保持两层：

1. 当前结论短句
2. 判定依据

例如：

```text
观察中
缩量｜突破量能偏弱｜无跌破量能要求｜回踩健康缩量
判定依据：量能未充分确认，需等待二次验证
```

### 9.3 方向提示

由于颜色已经表达方向，因此正文不强制重复写“偏多 / 偏空”。

但在 hover 中必须明确写出方向，避免色弱用户只能猜颜色。

## 10. 可访问性要求

- 颜色不能是唯一信息来源。
- 主标签文字必须独立表达状态。
- hover 中必须有明确文字：`当前方向：偏多 / 偏空 / 中性`。
- 红绿色对比需要足够清晰，背景采用浅底，文字采用深色。
- hover 与 tooltip 均需有 `aria-label` 或等价可读语义。

## 11. 测试要求

至少覆盖以下内容：

1. `passed / info / warning / failed` 是否分别映射为：
   - `可执行 / 观察中 / 谨慎看 / 暂不做`
2. `direction` 是否决定颜色，而不是 `status`
3. 标题 `i` hover 继续展示规则释义
4. 状态标签 hover 是否展示：
   - 交易含义
   - 规则状态
   - 当前方向
   - 当前原因
5. 顶部说明文案是否替换为用户语言
6. 用户可见 HTML 中不再出现：
   - `通过`
   - `警示`
   - `提示`
   - `失败`
   作为规则链主标签文案

## 12. 非目标

本次设计不包含：

- 三位一体后端判定逻辑变更
- 六段规则链的分类顺序调整
- 量能、均线、时空算法升级
- 周期详情区、综合判断区、级别总线的布局重排
- AI 综合判断卡的文案调整

本次只处理 **规则链状态表达方式**，即：

- 状态文案
- 方向颜色
- hover 释义
- 展示数据契约

## 13. 实施建议

建议拆成两步实施：

### 第一步：展示层替换

- 新增 `displayStatusLabel / direction / statusExplanation`
- 规则链组件替换旧标签文案
- 标题 hover 保持不变
- 新增状态标签 hover

### 第二步：回归与微调

- 调整不同方向下的卡片浅底色与边框色
- 检查桌面端六卡并排时的扫描感受
- 检查浅红 / 浅绿 / 浅灰在当前主题下的对比度
- 确认文案不会与综合判断区重复冲突
