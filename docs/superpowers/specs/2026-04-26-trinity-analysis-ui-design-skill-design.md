# 三位一体分析 UI 设计 Skill 设计

## 1. 背景

当前项目的三位一体分析页已经沉淀出较多高价值组件：

- 交易周期总线
- 规则链
- 周期详情
- 结构拓扑解释
- 各类 badge / hover / tooltip / 摘要卡

但这些组件在持续迭代中仍然容易出现一个共性问题：

1. 信息层级正确，但视觉表达不稳定
2. 组件能工作，但边距、留白、色彩、密度经常失衡
3. hover / tooltip 容易滑向“技术弹窗”或“字段堆砌”
4. 同一类语义在不同模块里，可能出现多套不一致的视觉语言

这类问题不是单次代码修补能根治的，而需要一个**跟项目一起走、团队成员都能复用的设计 skill**，把三位一体相关组件的 UI / UX 语言固化下来。

## 2. 设计结论

本次新增一个**仓库内项目 skill**，只服务三位一体相关组件的视觉与信息表达。

skill 采用：

- `规则 + 示例型`
- 默认视觉基调：`终端骨架 + 报告留白`
- 默认优先级：`可解释 > 可扫描 > 专业感 > 视觉张力`
- 默认多空配色：`偏多红 / 偏空绿`
- 默认用户可见文案：`自然中文`

它不是全站 design system，也不是营销页视觉规范，而是三位一体分析场景下的**组件级设计约束与推荐样板**。

## 3. 范围

### 3.1 首版覆盖范围

首版只覆盖三位一体相关组件，包括：

1. 交易周期总线
2. 规则链
3. 周期详情
4. 结构拓扑解释区
5. 结构拓扑 hover 卡
6. 上述区域中的 badge / hover / tooltip / 摘要卡 / 证据块

### 3.2 非目标

本次不覆盖：

1. 全站通用页面
2. 登录页、落地页、运营页
3. 后端字段设计
4. 策略判断逻辑本身
5. 完整设计系统 token 重建

## 4. Skill 目标

这个 skill 的目标不是“教模型做漂亮界面”，而是约束模型在三位一体分析场景下稳定产出以下结果：

1. 先结论、再摘要、再证据的层级
2. 清晰的 badge / 正文 / hover 职责边界
3. 稳定的边距、留白、密度和卡片层级
4. 保留多空色彩传统，但限制颜色滥用
5. 所有用户可见文案默认中文
6. 拓扑图、级别、摘要之间不得图文错配

## 5. 默认视觉基调

### 5.1 终端骨架

“终端骨架”指：

1. 信息分层明确
2. 状态、方向、约束、风险职责分离
3. 模块边界清晰
4. 更像研究工具，而不是营销卡片拼贴

### 5.2 报告留白

“报告留白”指：

1. 组件之间有呼吸感
2. 文案不过度贴边
3. 摘要块与证据块有阅读节奏
4. hover 卡更像小型研究说明卡，而不是调试面板

### 5.3 色彩原则

默认保留当前项目的交易语义：

1. 偏多使用红系
2. 偏空使用绿系
3. 中性、等待、观察优先使用灰蓝 / 石板色
4. 颜色只辅助表达状态，不代替中文文案

## 6. 硬规则

### 6.1 信息分层

1. 主内容必须先给结论，再给摘要，再给证据
2. badge 只承载短结论，不承载长解释
3. hover / tooltip 只能补充解释，不能承载用户必须先看到的核心信息
4. 相同语义不能在 badge、摘要、hover 里重复堆叠

### 6.2 颜色职责

1. 偏多红、偏空绿不反转
2. 中性 / 等待 / 观察类信息不抢多空主语义
3. 关键状态必须同时有中文文案
4. 不允许为了装饰引入高饱和干扰色破坏主判断

### 6.3 卡片与留白

1. 三位一体组件默认走“终端骨架 + 报告留白”
2. 卡片之间必须保留呼吸感，避免后台表单式贴合
3. 卡片内部优先 `标题 > 一句话摘要 > 结构化内容`
4. hover 卡、说明卡、拓扑卡必须有足够内边距，禁止贴边

### 6.4 Badge 规则

1. 一个 badge 只表达一个判断
2. badge 文案默认中文，并尽量具体到级别、状态、动作
3. 禁止暴露内部字段名、英文枚举、调试词
4. 同一区域的 badge 数量必须受控，避免药丸堆砌

### 6.5 Hover / Tooltip 规则

1. hover 标题必须明确“这是什么说明”
2. hover 默认回答三件事：
   - 这句话是什么意思
   - 为什么这么判断
   - 对交易或阅读有什么影响
3. hover 宽度必须足够，不能出现“右侧有空间但提前换行”
4. hover 中的结构图、级别、摘要必须来自同一级别
5. 用户可见描述必须为中文，不直接暴露 `render_payload`、`explainability` 等词

### 6.6 拓扑卡规则

1. 有结构图时，结构图优先展示客观结构本体
2. explainability 只有在完整时才进入解释层模式
3. explainability 缺失或不完整时，必须退回纯结构线 + 客观摘要
4. 拓扑摘要区统一使用“左标签 / 右正文”两列结构
5. 拓扑卡整体要像研究卡，不像技术调试面板

### 6.7 文案规则

1. 默认自然中文
2. 文案尽量具体到级别、条件、动作
3. 先给结论型短句，再给解释型长句
4. 除公认缩写如 `MA55 / MA233` 外，避免中英混杂

### 6.8 自检规则

每次改三位一体相关 UI，都必须至少自检：

1. 主结论是否一眼可见
2. 是否存在重复表达
3. 颜色是否只承担有限职责
4. hover 是否只做补充解释
5. 文案是否自然中文
6. 边距、留白、密度是否平衡

## 7. 组件示例模板

### 7.1 交易周期总线

推荐结构：

1. 顶部：组合名称 + 当前综合状态
2. 中部：一句话摘要
3. 下部三层：
   - 当前动作状态
   - 子级综合判断依据
   - 父级约束

规则：

1. 当前动作状态只表达“现在能不能做、最多做到什么程度”
2. 子级综合判断依据只放支撑当前动作判断的子级证据
3. 父级约束必须单独成层，不能混入子级依据
4. 父级约束 hover 看父级拓扑，其他执行相关 hover 看子级拓扑

### 7.2 规则链

推荐结构：

1. 左侧：规则名
2. 右侧：状态标签
3. 下方：一句话原因
4. hover：解释规则定义、当前状态、交易影响

规则：

1. 状态标签和方向标签职责分离
2. 主标签表达状态，不承担全部证据
3. 规则链是判断框架，不是证据仓库

### 7.3 周期详情 / 结构拓扑解释

推荐结构：

1. 顶部：当前级别主结论
2. 中部：结构解释摘要
3. 下部证据区：
   - 结构类型
   - 当前段 / 下一确认
   - 结构拓扑
   - 风险 / 失效条件

规则：

1. 拓扑图属于证据区，不抢主结论位
2. 先说明当前结构与阶段，再展开细锚点
3. 若结构不可完整解释，必须明确降级

### 7.4 Hover 拓扑卡

推荐结构：

1. 顶部：说明标题 + 级别标识
2. 中部：结构图
3. 底部：两列摘要
   - 当前结构
   - 当前阶段 / 原始描述
   - 下一确认 / 数据状态

规则：

1. annotated 与 raw-lines 必须可区分，但不靠英文术语直接出屏
2. pure lines fallback 也必须保持正式卡片感
3. 结构图是视觉中心，周边说明为辅助

## 8. Skill 形态

### 8.1 形态选择

本 skill 采用“规则 + 示例型”：

1. 前半部分是默认硬规则
2. 后半部分是三位一体组件样板

这样既能约束改动，又能给团队成员复用时提供明确参照。

### 8.2 仓库落点

该 skill 以**仓库内项目 skill**方式存在，随项目版本一起演进，供团队成员共同复用。

首选落点：

`skills/trinity-analysis-ui-design/`

其中至少包含：

1. `SKILL.md`
2. 如有必要，可补少量参考文件或示例文件

## 9. 使用触发

未来当模型执行以下任务时，应优先触发该 skill：

1. 修改三位一体分析页视觉样式
2. 调整交易周期总线、规则链、周期详情、拓扑说明区的 UI
3. 设计新的 hover / tooltip / 摘要卡 / 证据块
4. 优化 spacing、层级、色彩、badge 语义
5. 审查三位一体组件是否符合项目设计语言

## 10. 验收标准

首版 skill 完成后，应满足：

1. 能明确告诉模型哪些是硬规则，哪些是推荐模板
2. 能覆盖交易周期总线、规则链、周期详情、拓扑 hover 卡四类核心场景
3. 能稳定约束中文文案、多空色彩、hover 职责边界、两列摘要结构
4. 团队成员看到 skill 后，可以直接用同一语言继续改组件，而不是凭感觉重写

## 11. 后续路线

首版完成后，后续可继续迭代：

1. 把三位一体常见 hover 模板做成固定示例库
2. 补一组“正例 / 反例”截图或 HTML mock 参考
3. 视需要再扩展到全站分析类页面组件
