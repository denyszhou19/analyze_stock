# 结构可解释性 UI 设计

## 背景

上一轮重构已经把 `execution_phase / execution / trading_decision` 这条 execution-first 链路从后端打通到了 AI payload、AI prompt 和分析页摘要层，但用户在分析页面上理解结构时，仍然存在三个关键问题：

- 看得到“当前阶段 / 执行建议 / 结构原型”，但看不出当前这轮结构从哪里开始计算。
- 看得到结构拓扑图，但不知道当前到底走到哪一段、下一段预期是哪一段。
- “结构原型”和“结构拓扑识别结果”高度重复，页面没有提供新增认知。

此外，现有结构详情主要依赖 hover 展示，浮层阅读区域过窄，用户很难在单屏内看完整个结构说明，交互成本过高。

这次不继续沿用“大而泛”的结构 phase/execution spec 直接往前推，而是单独补一份聚焦的“结构可解释性 UI spec”，只解决以下三件事：

1. 结构起点怎么标。
2. 当前段 / 下一段怎么在图上表达。
3. 原型卡怎么和拓扑图区分，不再重复。

## 目标

- 让用户一眼看出“当前这轮结构从哪里开始算”。
- 让用户在图上直接知道“现在走到哪一段、下一段预期是哪一段”。
- 让“结构原型”不再重复“结构拓扑”的主标签，而是补充解释“为什么更像这个原型、备选原型是什么”。
- 优化结构详情交互，让拓扑相关信息尽量在一个屏幕内看全，不依赖狭窄 hover 浮层完成主阅读。
- 本次先落地方案 1 的静态可解释性增强，但数据结构要为未来升级到方案 2 的图文联动预留接口。

## 非目标

- 不重写结构识别算法本身。
- 不修改 `execution / trading_decision` 的后端决策逻辑。
- 不在本次把页面升级为完整交互式结构分析器，不引入复杂选中态或鼠标联动体系。
- 不新增新的交易规则。
- 不删除现有结构拓扑图、prediction、峰值分析、左侧风险警示等区域，只做层级重排和解释性增强。

## 术语统一

为避免后续文档和实现混淆，本 spec 统一使用以下术语：

- `结构起点`
  当前被识别结构的第一个确认拐点。
- `当前阶段锚点`
  当前 `prediction.current_stage` 对应的图上节点。
- `当前段`
  当前阶段对应、用户此刻最该关注的那一段线段。
- `下一段预期`
  从当前阶段走向 `prediction.next_stage` 的预期线段。

本 spec 不再使用“最近一次阶段切换点”这个模糊表述。

## 总体方案

本次采用“方案 1：轻量标注型”，但在数据模型上预留“方案 2：图文联动型”的接口思想。

### 本次直接做的内容

- 在拓扑图上标出结构起点。
- 给标准结构显示 `a1... / b1... / c1... / d1...` 节点编号。
- 高亮当前段。
- 用虚线或淡色预览下一段预期。
- 让“结构原型”卡从“重复结构标签”改成“主原型 + 备选原型 + 判断理由”。
- 把结构图从“hover 内容的一部分”提升为结构区主体内容，降低 hover 依赖。

### 本次不直接做但要预留的数据接口

- 节点 hover 与侧边解释面板联动。
- 点击某个节点或线段后，高亮对应解释项。
- `current_segment / next_segment_preview` 的交互态切换。

## 数据与标注规则

### 1. 现有数据继续复用

本次不新造拓扑底座，继续使用以下数据作为来源：

- `structure_details.render_payload`
  作为前端画图底座。
- `structure_details.prediction.current_stage / next_stage`
  作为当前阶段与下一阶段的语义来源。
- `structure.archetype`
  作为原型卡来源。

### 2. 新增 explainability 标注层

在 `structure_details` 下新增 `explainability`：

```ts
structure_details: {
  // 现有字段保留
  render_payload?: StructureRenderPayload;
  prediction?: Record<string, unknown>;

  explainability?: {
    structure_family: 'A' | 'B' | 'C' | 'D' | 'complex' | 'unfinished';
    structure_start_point_id: string | null;
    current_point_id: string | null;
    current_segment: {
      from_point_id: string;
      to_point_id: string;
      label: string;
    } | null;
    next_segment_preview: {
      from_point_id: string;
      to_point_id: string;
      label: string;
      status: 'projected' | 'completion' | 'direction_choice';
    } | null;
    point_labels: Array<{
      point_id: string;
      label: string;
      role: 'start' | 'current' | 'normal' | 'projected';
    }>;
    segment_labels: Array<{
      segment_id: string;
      from_point_id: string;
      to_point_id: string;
      label: string;
      role: 'current' | 'projected' | 'normal';
    }>;
    display_reason: string;
  };
}
```

说明：

- 本次不要求一开始就做复杂交互，但 `point_id / segment_id` 不能写死成纯文案，必须可供后续联动使用。
- `point_id` / `segment_id` 的具体编码可以简洁稳定，例如 `a1`、`a1-a2`。

### 3. 结构起点定义

- `structure_start_point_id` 固定定义为：当前被识别结构的第一个确认拐点。
- 它不等于图最左点。
- 它也不等于最近一次价格波动起点。
- 如果图左侧仍保留更早的上下文笔，这些笔只作为背景上下文，不参与本轮结构编号。

### 4. 节点与线段编号规则

- 标准结构 `A / B / C / D`：
  - 节点编号统一为 `a1 / a2 / ...`、`b1 / b2 / ...`、`c1 / c2 / ...`、`d1 / d2 / ...`
  - 线段标签统一为 `a1→a2`、`a2→a3` 等。
- 页面主展示优先使用“点编号 + 线段编号”，不直接把黑话段位（如 `A1 / A2 / A3`）作为主标签。
- 黑话解释可以在补充说明区保留，但不作为第一阅读入口。

### 5. 当前段 / 下一段定义

- `current_point_id` 来自 `prediction.current_stage` 对应节点。
- 若 `prediction.current_stage` 不能一对一映射到标准编号节点，则后端必须回退到“当前最接近的已确认锚点”，并把映射依据写入 `display_reason`。
- `current_segment` 表示用户此刻最该关注的那一段，默认展示为：
  - `当前段：a3→a4`
- `next_segment_preview` 表示当前结构的下一步预期，默认展示为：
  - `下一段：a4→a5`
- 如果 `next_stage` 已经表示“结构完成 / 方向选择”，则不强制画下一段虚拟线，而是显示结构完成提示。
- 当 `next_stage` 属于“结构完成 / 方向选择”这类非线段状态时，`next_segment_preview` 应为 `null`，并由 `display_reason` 提供文字说明。

### 6. 特殊情况规则

- `复杂结构 / 结构未完成`
  - 不强行套 `a1...` 这类标准编号。
  - 只标结构起点、当前点、当前笔。
- `峰值切片 override`
  - 若系统战术焦点已切到右侧结构，则结构起点取右侧结构的第一个确认拐点。
  - 左侧结构保留为灰色背景上下文，不参与本轮编号。
- `is_current = true` 的进行中笔
  - 保留显示。
  - 但视觉上要与“下一段预期”区分，避免把“正在形成”和“尚未开始”混为一谈。

### 7. 原型卡数据分工

原型卡不再只展示 `primary`。

原型卡默认展示：

- 主原型
- 备选原型
- 判断理由

规则：

- 主原型优先取 `archetype.primary`
- 备选原型取 `archetype.alternatives`
- 判断理由优先取 `archetype.reason`
- 如果 `primary` 与拓扑主标签相同，这是允许的；但原型卡必须通过“理由”或“备选原型”体现信息增量

## 页面交互与展示规则

### 1. 结构区层级重排

结构区域分成三层：

1. 摘要层
   - 当前阶段
   - 执行建议
   - 结构原型
2. 结构拓扑主视图
   - 作为主体内容直接可见
3. 补充说明层
   - 峰值分析
   - 左侧风险提示
   - judgment criteria
   - prediction 细节

### 2. 结构拓扑主视图规则

拓扑图主体必须直接可见以下标注：

- `结构起点`
  - 通过明显但不过分抢眼的视觉标识显示，例如空心高亮点或“起点”标签
- `当前点`
  - 通过主高亮色或实心强调
- `当前段`
  - 通过加粗或高亮线强调
- `下一段预期`
  - 通过虚线或淡色线展示
- `进行中笔`
  - 仍保留虚线，但视觉区分于“下一段预期”

### 3. 编号显示规则

- 起点编号必须可见
- 当前点编号必须可见
- 下一目标点编号必须可见
- 其他点编号在密集场景可以做稀疏显示，但不能影响用户理解当前结构路径

在图旁或图下补一条极短结构路径说明：

- `起点：a1`
- `当前：a4`
- `下一段：a4→a5`

### 4. 原型卡去重规则

原型卡不再承担“告诉用户图上是什么结构”的主职责，改为承担“解释为什么判成这个原型”。

原型卡展示结构建议为：

- 第一行：主原型
- 第二行：备选原型
- 第三行：为什么判成这个原型

如果没有备选原型，则显示“主原型 + 判断理由”。

### 5. Hover / Tooltip 交互优化

这次必须显式优化现有“hover 太窄、单屏看不全”的问题。

规则：

- 结构图本体不应只存在于 hover 内。
- hover / tooltip / popover 只承载补充说明，不承担主阅读职责。
- 若仍保留浮层：
  - 宽度必须足够支持单屏阅读主要内容
  - 高度受视口约束，内部滚动
  - 不允许依赖极小热点长时间悬停完成整块阅读

推荐实现方向：

- 结构图直接嵌入主卡片内容
- 复杂说明改为可展开区域或点击式面板
- hover 仅保留轻量提示

### 6. 当前阶段与拓扑图的轻量联动

本次只做轻量联动，不做复杂交互：

- “当前阶段”卡里的阶段名必须对应到图上的当前点 / 当前段
- “结构原型”卡不负责告诉用户图上在哪一段
- 用户看完摘要层与拓扑图后，必须能回答：
  - 这轮结构从哪开始
  - 现在在图上哪里
  - 下一步大概看哪一段

### 7. 兼容与回退

- 现有 prediction 区块保留
- 现有结构 badge 保留，但降级为辅助信息
- 现有峰值分析 / 左侧风险警示 / judgment criteria 保留
- 如果 `explainability` 数据缺失：
  - 页面不得白屏或报错
  - 回退到现有拓扑图 + prediction 文案展示

## 验收标准

### 1. 用户可理解性验收

用户打开任一级别结构区后，不借助额外解释，能直接回答：

- 这轮结构从哪里开始算
- 现在走到哪一个点 / 哪一段
- 下一段预期看哪里

当页面显示 `A五段式` 时，用户必须能在图上找到 `a1` 起点，并理解当前是 `a3 / a4 / a5` 中的哪一段。

### 2. 结构图展示验收

拓扑图主区域中必须可见：

- 结构起点标识
- 当前点标识
- 当前段高亮
- 下一段预期标识

若结构属于 `A / B / C / D` 标准原型，图上必须出现对应编号体系：

- `a1...`
- `b1...`
- `c1...`
- `d1...`

若是 `复杂结构 / 结构未完成`，页面不得伪造标准编号。

### 3. 原型卡去重验收

- 原型卡不能只显示一个与拓扑 badge 相同的结构名然后结束。
- 原型卡至少包含以下三项中的两项：
  - 主原型
  - 备选原型
  - 判断理由

### 4. 交互与布局验收

- 用户不需要依赖 hover 才能读懂核心结构信息。
- 拓扑图应直接在结构区主体内可见。
- 若仍保留浮层：
  - 宽度足够单屏阅读主要内容
  - 高度受视口约束，内部滚动
  - 不出现“鼠标稍微移开就看不全”的情况

### 5. 数据与实现验收

- UI 不直接从纯文案反推结构起点、当前段、下一段。
- 数据层必须提供结构化锚点信息，至少支撑：
  - 起点 point id
  - 当前 point id
  - 当前 segment
  - 下一段 preview
- 编号与 current/next segment 的数据结构不能写死成最终文案，以便后续升级为图文联动。

### 6. 兼容性验收

- explainability 数据缺失时，页面仍能回退到现有拓扑图 + prediction 展示
- 现有结构 badge、prediction、峰值分析、左侧风险警示继续可用

## 交付范围

本 spec 只覆盖：

- 结构可解释性 UI
- explainability 标注数据
- 结构图主视图与补充说明交互

不覆盖：

- execution-first 规则本身
- 新的仓位管理与风控规则
- AI prompt 或 AI 结构解读策略
